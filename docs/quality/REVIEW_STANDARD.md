# Syllanix: стандарт доказательной редакторской проверки

Цель: **точность, полезность и понятность**, а не максимальная длина главы. Применяется ко всем 56 главам, решениям и SVG. Версия: 2026-11-02.

## Основное правило

Каждое предложение, пример, схема и задача должны быть либо (а) проверены по первоисточнику и исполнению кода, либо (б) явно отмечены как эвристика/упрощение. Не придумывать подтверждения и не подменять анализ количественными метриками.

Приоритет доказательств: **Python Language Reference** (семантика) → **Python Library Reference** (API) → **официальный Python Tutorial** (педагогическое объяснение) → исполняемые регрессионные проверки → рецензирование. Если источники расходятся по версиям, фиксировать версию. Ссылки на источники должны вести на конкретный раздел.

## Матрица качества — 100 баллов

| Критерий | Вес | Что проверяется |
|---|---:|---|
| Техническая корректность | 20 | Семантика, версии, граничные случаи, точные утверждения об ошибках |
| Педагогическая доступность | 15 | Предпосылки, ясные термины, движение от простого к сложному |
| Глубина объяснений | 10 | Причины, механика, ограничения, а не только синтаксис |
| Прикладная полезность | 10 | Реалистичные ситуации без искусственной сложности |
| Примеры и их воспроизводимость | 10 | Запуск, ожидаемые результаты, ошибки, порядок выполнения |
| Упражнения и решения | 10 | Различные уровни, самостоятельное мышление, корректные решения |
| SVG: смысл и визуальный язык | 10 | Правильность стрелок, подписи, визуальная иерархия, отсутствие перегруза |
| Доступность и адаптация | 5 | Контраст, масштаб, SVG title/desc/alt, читаемость без цвета |
| Связность и отсутствие дублей | 5 | Проверка соседних глав, концептов и переходов |
| Подтверждение и сопровождение | 5 | Источники, даты, тесты, замечания и статус проверки |
| **Всего** | **100** | |

**Оценивание каждой строки:** от 0 до 5, с фактическими доказательствами. Итог: сумма (балл / 5 × вес). Если нет независимой проверки, помечать оценку как предварительную. Не путать субъективную оценку красоты с объективно проверяемой корректностью.

**Условия принятия:** 0 известных критических ошибок; не менее 90/100 по матрице для отметки «рецензировано»; проверены все исполняемые фрагменты и решения; проверены все затронутые SVG и связи; нет утверждений о тестировании без протокола. Отдельно фиксировать «не проверено» вместо оценки 5/5. Отсутствие результатов пользовательского тестирования нельзя выдавать за доказанную понятность.

## Чек-лист проверки каждой главы

1. Сопоставить пункты оглавления и `concepts_introduced` с официальной спецификацией/библиотекой, зафиксировать отсутствующие предпосылки.
2. Проследить утверждения, включая слова «всегда», «никогда», «только», «не может» и проверить контрпримеры.
3. Исполнить код в поддерживаемой версии Python, сверить stdout/stderr и исключения. Потенциально бесконечные циклы — только с ограничением по времени в изолированной среде. Не запускать сетевой, файловый или опасный код без изоляции.
4. Проверить крайние случаи: пустые входы, нулевые значения, отрицательные значения, ошибки типов, вложенные конструкции, изменение переменных.
5. Проверить каждое упражнение и решение независимо; формулировка должна иметь проверяемый критерий успеха и не требовать неизвестных концептов.
6. Сверить главу с соседними главами, чтобы не дублировать продвинутые темы и не использовать необъяснённые конструкции.
7. Для каждого SVG: проверить XML, совпадение смысла диаграммы и исполняемого кода, подписи ветвей, направление стрелок, отсутствие пересечений, читаемость в 320px и 740px, контраст, `viewBox`, `title` и `desc`, отсутствие внешних ресурсов/скриптов. Цвет не должен быть единственным носителем смысла.
8. Проверить Markdown-навигацию, имена файлов, ссылки и опубликованную HTML-версию. Сборка сайта предпочтительнее ручных правок HTML, если доступна.
9. Сохранить таблицу «наблюдение → доказательство → изменение → проверка → остаточный риск».
10. Граница работы: одна глава считается проверенной лишь после завершения всех пунктов; наличие файла или иллюстрации не является доказательством качества.

## Договорённости для графики

Палитра: нейтральный фон, тёмные подписи, единый зелёный для «действие/продолжить», янтарный для проверки условия, сдержанный красный для `break`. Явно подписывать ветви («да», «нет») и тип перехода («к проверке условия», «следующая итерация»). Визуальные элементы должны соответствовать действительному управлению программой, а не только выглядеть красиво.

Схемы в `book/illustrations/` и `illustrations/` должны быть идентичными. Проверка проекта включает пути к рисункам, разумный размер файла и запрет небезопасных SVG-конструкций.
