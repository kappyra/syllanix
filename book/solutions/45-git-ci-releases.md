# Решения к главе 45

## 1. Первый репозиторий {#sol-ch45-01}

```console
$ git init
Initialized empty Git repository in /home/user/project/.git/
$ printf 'print("привет")\n' > hello.py
$ git add hello.py
$ git commit -m "Добавить первую программу"
[main (root-commit) 9f8e7d6] Добавить первую программу
 1 file changed, 1 insertion(+)
$ printf 'print("пока")\n' > hello.py
$ git add hello.py
$ git commit -m "Изменить приветствие"
[main b7e4d91] Изменить приветствие
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git log --oneline
b7e4d91 Изменить приветствие
9f8e7d6 Добавить первую программу
```

`git add` помещает изменение в **область подготовки** (staging area) — то, что
войдёт в следующий коммит. `git commit` создаёт неизменяемую запись в истории
из подготовленных изменений. Между ними можно менять файлы дальше: в коммит
попадёт только подготовленное состояние.

## 2. Статус и diff {#sol-ch45-02}

`git status` показывает, какие файлы изменены, какие подготовлены и какие не
отслеживаются. `git diff` показывает **содержание** изменений: какие строки
добавлены и удалены. Перед коммитом это нужно, чтобы не зафиксировать лишнее
(отладочные `print`, временные файлы, секреты) и убедиться, что изменение
действительно то, которое задумано.

## 3. Хорошее сообщение коммита {#sol-ch45-03}

- `fix` → `Исправить падение при пустом списке задач`
- `update code` → `Вынести расчёт скидки в отдельную функцию`
- `правки после обеда` → `Уточнить сообщение об ошибке валидации`

Правило: сообщение отвечает на вопрос «что и зачем изменено», написано в
повелительном наклонении, не содержит слов «правки», «разное», «мелочи».
Хорошее сообщение читается как инструкция к изменению и понятно без открытия
diff.

## 4. Ветка и слияние {#sol-ch45-04}

```console
$ git switch -c feature/calc
$ # изменения и коммиты
$ git switch main
$ git merge feature/calc
```

Если обе ветки изменили одну и ту же строку, возникает конфликт: Git
останавливает слияние и помечает конфликтующие участки в файлах. Нужно вручную
выбрать (или скомбинировать) правильный вариант, удалить маркеры конфликта,
затем `git add` и `git commit`. Конфликт — сигнал, что изменения пересеклись,
а не признак поломки.

## 5. Что не коммитить {#sol-ch45-05}

```text
.venv/
__pycache__/
*.pyc
build/
dist/
*.egg-info/
.env
*.pem
.pytest_cache/
```

`.env` содержит конфигурацию и секреты (ключи API, пароли). Репозиторий
копируется, клонируется и часто передаётся третьим лицам; попавший в историю
секрет остаётся в ней навсегда и должен считаться скомпрометированным.
Секреты хранят вне репозитория, а в репозитории держат `.env.example` с
фиктивными значениями.

## 6. Красный конвейер {#sol-ch45-06}

Правильные действия:

1. Открыть лог упавшего шага и прочитать ошибку.
2. Воспроизвести падение локально той же командой.
3. Исправить причину, а не тест.
4. Отправить коммит с исправлением; при необходимости добавить тест на
   найденный дефект.

Чего делать нельзя: мержить при красном конвейере; удалять или пропускать
падающий тест без понимания причин; отключать проверку «на время»; менять CI,
чтобы он не запускал проблемный шаг.

## 7. Семантическое версионирование {#sol-ch45-07}

- (а) новый необязательный аргумент функции — `MINOR` (`1.4.2` → `1.5.0`);
- (б) удалён параметр — несовместимое изменение, `MAJOR` (`1.4.2` → `2.0.0`);
- (в) исправлена опечатка в сообщении — `PATCH` (`1.4.2` → `1.4.3`).

Оговорка: если внешний код полагался на текст сообщения об ошибке, формально
это тоже может быть несовместимым изменением — но по принятому соглашению
сообщения об ошибках не считаются частью стабильного API, если не объявлено
обратное.

## 8. Журнал изменений {#sol-ch45-08}

```text
# Changelog

## [1.5.0] — 2026-11-01
### Добавлено
- Фильтрация задач по статусу.

### Исправлено
- Задачи с пустым названием больше не сохраняются.
```

Разделы нужны, чтобы читатель быстро понял: совместимо ли обновление, что
появилось нового, какие дефекты устранены. Пропуск раздела «Исправлено» скрывает
важную информацию для тех, кто страдал от дефекта.

## 9. Метрики и оповещения {#sol-ch45-09}

| Метрика | Оповещение |
|---|---|
| доступность (доля успешных запросов) | ниже 99 % за 5 минут |
| задержка (95-й процентиль) | выше 1 с за 10 минут |
| доля ошибок 5xx | выше 1 % за 5 минут |
| свободная память/диск | ниже 10 % |

Оповещение без действия бесполезно: оно приучает игнорировать сигналы. У
каждого оповещения должен быть владелец, порог и инструкция, что делать.

## 10. План отката {#sol-ch45-10}

До выпуска `1.5.0` должно быть готово:

1. **Артефакт предыдущей версии** (`1.4.2`) доступен и проверен.
2. **Одна команда отката** (или кнопка в системе доставки), известная команде.
3. **Обратная совместимость данных**: миграции базы данных, которые можно
   откатить или которые совместимы с прежней версией кода.
4. **Критерий отката**: например, доля ошибок выше 2 % в течение 15 минут.
5. **Оповещение ответственного** и запись в журнал выпусков.

Смысл: откат — заранее отрепетированный сценарий, а не импровизация под
давлением.
