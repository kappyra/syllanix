# Решения к главе 38

Решения подчёркивают разницу между «работает» и «работает детерминированно».
Там, где вывод зависит от планировщика, примеры приведены как иллюстративные:
в учебной песочнице такие проверки не запускаются.

## 1. Классификация задач {#sol-ch38-01}

1. **Скачивание десяти страниц** — задача, связанная с вводом-выводом. Почти
   всё время уходит на ожидание сети. Подойдут потоки или `asyncio`; процессы
   здесь только добавят накладных расходов.
2. **Вычисление миллиона простых чисел** — задача, связанная с вычислениями.
   Цикл занимает процессор и не освобождает GIL, поэтому потоки не ускорят её.
   Нужны процессы — или более быстрый алгоритм, что обычно важнее.
3. **Чтение большого файла** — ввод-вывод. Потоки помогают, если файл читается
   параллельно с другой работой; но если чтение одно, последовательный код
   проще. Для сетевых файловых систем выигрыш заметнее.
4. **Сортировка списка из ста элементов** — небольшая вычисляемая задача.
   Последовательный код быстрее любого параллельного варианта: накладные
   расходы на запуск потоков и передачу данных больше самой работы.

Общий принцип: сначала измеряют, где уходит время, и только потом добавляют
конкурентность. «Много задач» само по себе не аргумент.

## 2. Первый поток {#sol-ch38-02}

```python exec
import threading

results: list[int] = []
lock = threading.Lock()


def add(number: int) -> None:
    with lock:
        results.append(number)


threads = [threading.Thread(target=add, args=(n,)) for n in (3, 1, 2)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
print(sorted(results))
```

```output
[1, 2, 3]
```

Сортировка нужна, потому что порядок добавления зависит от планировщика.
Блокировка защищает список от одновременного изменения; для одного `append`
в CPython её роль невелика, но привычка защищать общее состояние важна.

## 3. Пул потоков {#sol-ch38-03}

```python exec
from concurrent.futures import ThreadPoolExecutor


def cube(value: int) -> int:
    return value ** 3


with ThreadPoolExecutor(max_workers=3) as executor:
    print(list(executor.map(cube, range(1, 9))))
```

```output
[1, 8, 27, 64, 125, 216, 343, 512]
```

`executor.map` возвращает результаты в порядке входных данных, а не в порядке
завершения задач: контракт `map` сохраняет соответствие. Если важен порядок
завершения, используют `as_completed`, но тогда и порядок результатов будет
другим.

## 4. Защита счётчика {#sol-ch38-04}

```python exec
import threading

counter = 0
lock = threading.Lock()


def increment() -> None:
    global counter
    for _ in range(5000):
        with lock:
            counter += 1


threads = [threading.Thread(target=increment) for _ in range(3)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
print(counter)
```

```output
15000
```

Блокировка делает операцию «прочитать — сложить — записать» неделимой для
других потоков. Без неё возможна потеря обновлений: поток прочитал старое
значение, другой успел записать новое, и первое перезаписало второе. GIL
переключает потоки между байткодами, но не отменяет эту гонку.

## 5. Объяснение гонки {#sol-ch38-05}

`counter += 1` — не одна операция, а несколько шагов: прочитать значение
`counter`, вычислить сумму, записать результат обратно. Планировщик может
переключить поток между этими шагами. Пусть оба потока прочитали `100`:
первый записал `101`, второй тоже записал `101` — одно из двух увеличений
потерялось. В итоге получится не `200000`, а меньше.

GIL не спасает, потому что он обеспечивает исполнение байткода одним потоком
в единицу времени, но не делает последовательность байткодов атомарной.
Переключение как раз и происходит между шагами операции. Защита инварианта —
задача программиста: нужна блокировка вокруг составной операции или
потокобезопасная структура.

```text
поток 1: прочитать 100
поток 2: прочитать 100
поток 1: записать 101
поток 2: записать 101   ← обновление потока 1 потеряно
```

## 6. Очередь задач {#sol-ch38-06}

```python exec
import queue
import threading

tasks: queue.Queue[int] = queue.Queue()
results: list[int] = []


def producer() -> None:
    for number in range(5):
        tasks.put(number)
    tasks.put(-1)


def consumer() -> None:
    while True:
        number = tasks.get()
        if number == -1:
            break
        results.append(number * 10)


worker = threading.Thread(target=consumer)
worker.start()
producer()
worker.join()
print(sorted(results))
```

```output
[0, 10, 20, 30, 40]
```

Очередь сама синхронизирует доступ: `put` и `get` потокобезопасны. Поток
потребителя блокируется на `get`, пока не появится задача, и просыпается,
когда производитель что-то положит. Маркер `-1` завершает цикл — без него
потребитель ждал бы вечно.

## 7. Правда и мифы о GIL {#sol-ch38-07}

(а) **Неверно.** GIL не ускоряет потоки; для вычислений он делает их
бесполезными в смысле параллелизма.
(б) **Верно.** При ожидании ввода-вывода поток освобождает GIL, и другие
потоки продолжают работу — поэтому потоки полезны для сети и файлов.
(в) **Неверно.** GIL защищает внутренние структуры интерпретатора, а не ваши
данные. Составные операции над общими объектами всё равно требуют блокировки.
(г) **Неверно.** GIL — деталь реализации CPython; язык Python его не
гарантирует, а free-threaded сборка без GIL официально поддерживается
начиная с 3.14.
(д) **Верно.** Процессы не делят память и исполняются независимо, поэтому
обходят ограничение GIL для вычислений — ценой накладных расходов на запуск и
сериализацию данных.

## 8. Потоки или процессы {#sol-ch38-08}

Если функция считает хэши строк, она занята вычислениями: время уходит на
работу процессора, а GIL не даёт потокам исполнять байткод одновременно.
Значит, нужны процессы — при условии, что вычислений достаточно много, чтобы
оправдать запуск пула. Для маленьких строк накладные расходы могут съесть
выигрыш, и последовательный код окажется быстрее.

Если функция вместо вычислений читает файлы, задача становится связанной с
вводом-выводом. Потоки подойдут лучше: пока один ждёт диск, другой читает
следующий файл. Процессы тоже сработают, но обойдутся дороже.

```python
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor

# вычисления: процессы
with ProcessPoolExecutor() as executor:
    hashes = list(executor.map(hash_text, texts))

# чтение файлов: потоки
with ThreadPoolExecutor(max_workers=8) as executor:
    contents = list(executor.map(read_file, paths))
```

## 9. Проверка потокобезопасности {#sol-ch38-09}

```python exec
import threading

counters: dict[str, int] = {"total": 0}
lock = threading.Lock()


def add(amount: int) -> None:
    for _ in range(1000):
        with lock:
            counters["total"] += amount


threads = [threading.Thread(target=add, args=(1,)) for _ in range(4)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
print(counters["total"])
print(counters["total"] == 4000)
```

```output
4000
True
```

Проверка детерминирована, потому что блокировка сериализует все обновления:
итог не зависит от порядка потоков. Если убрать блокировку, результат станет
непредсказуемым — тест начнёт «мигать». Именно поэтому тесты на конкурентный
код проверяют инварианты (например, «сумма равна ожидаемой»), а не
конкретный порядок событий.

## 10. Мини-проект: параллельная загрузка {#sol-ch38-10}

Задача — ввод-вывод, поэтому выбираем пул потоков. Ограничение
`max_workers` защищает сеть и сервер от перегрузки; ошибки одной загрузки не
должны ронять остальные, поэтому каждая задача возвращает результат или
сообщение об ошибке.

```python exec
from concurrent.futures import ThreadPoolExecutor


def fetch(url: str) -> int:
    if "broken" in url:
        raise ConnectionError(f"не удалось загрузить {url}")
    return len(url) * 10


def fetch_all(urls: list[str], max_workers: int = 3) -> list[object]:
    results: list[object] = []
    with ThreadPoolExecutor(max_workers=max_workers) as executor:
        futures = {executor.submit(fetch, url): url for url in urls}
        for future in futures:
            url = futures[future]
            try:
                results.append(future.result())
            except ConnectionError as exc:
                results.append(str(exc))
    return results


print(fetch_all(["https://a.example/1", "https://broken.example/2", "https://a.example/3"]))
```

```output
[190, 'не удалось загрузить https://broken.example/2', 190]
```

Порядок результатов здесь соответствует порядку `urls`, потому что словарь
`futures` сохраняет порядок вставки, а перебор идёт по нему. В рабочем коде
результаты складывают вместе с URL, чтобы не зависеть от порядка. Таймаут
задаётся в самой функции загрузки; общий таймаут пула не предусмотрен, и это
важно помнить: зависшая задача займёт поток.

## Ответы на вопросы для самопроверки

1. Конкурентность — перекрытие задач во времени; параллелизм — их
   одновременное исполнение на разных ядрах.
2. Потоки освобождают GIL на время ожидания, поэтому ждут параллельно; при
   вычислениях GIL не даёт исполнять байткод одновременно.
3. GIL — блокировка интерпретатора CPython; она не делает составные операции
   над общими данными атомарными.
4. Блокировка делает критическую секцию недоступной для других потоков, пока
   она занята, и защищает инвариант.
5. Процессы имеют отдельную память; обмен идёт через аргументы, очереди и
   сериализацию.
6. Пул ограничивает число потоков и переиспользует их, не создавая поток на
   каждую задачу.
7. Иначе два потока могут захватить блокировки в разном порядке и
   заблокировать друг друга навсегда.
