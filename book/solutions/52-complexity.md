# Решения к главе 52

Решения отделены от условий. Здесь важнее рассуждение, чем код: для каждого
ответа нужно назвать порядок роста и объяснить, что именно растёт. Числа в
выводе проверены на Python 3.14.4 и могут отличаться на другой машине там,
где речь о времени.

## 1. Оценка по коду {#sol-ch52-01}

Разберём фрагменты по порядку.

1. Один цикл по `items` с печатью — `O(n)`: работа пропорциональна числу
   элементов.
2. Два вложенных цикла по тем же данным — `O(n ** 2)`: число пар растёт как
   квадрат.
3. Цикл с проверкой `item in seen_set` — `O(n)` в среднем: сама проверка в
   множестве стоит `O(1)`, а цикл делает `n` шагов. Если бы вместо множества
   был список, получилось бы `O(n ** 2)`.
4. Цикл `while n > 1: n = n // 2` — `O(log n)`: на каждом шаге вход
   уменьшается вдвое, поэтому шагов примерно `log2(n)`.
5. `print(items[0])` — `O(1)`: доступ по индексу не зависит от размера списка.

Во всех случаях мы оценивали худший или типичный случай: для проверки в
множестве — типичный (при плохом хешировании он деградирует), для остальных —
худший. Проверить это можно счётчиком операций.

```python exec
def pairs_count(items):
    operations = 0
    for first in items:
        for second in items:
            operations += 1
    return operations

def single_pass(items):
    operations = 0
    for item in items:
        operations += 1
    return operations

data = list(range(500))
print("один проход:", single_pass(data))
print("все пары:", pairs_count(data))
print("во сколько раз больше:", pairs_count(data) // single_pass(data))
```

```output
один проход: 500
все пары: 250000
во сколько раз больше: 500
```

При `n = 500` вложенный цикл сделал в 500 раз больше работы, и с ростом `n`
это отношение растёт — вот что означает `O(n ** 2)`.

## 2. Константа или рост {#sol-ch52-02}

Точка пересечения находится из уравнения `500n = n ** 2`, то есть `n = 500`.
До этого значения квадратичная функция дешевле по числу операций, после —
линейная. Проверим таблицей.

```python exec
def linear_steps(n):
    return 500 * n

def quadratic_steps(n):
    return n * n

print(f"{'n':>6} {'500n':>10} {'n*n':>12} {'линейный дешевле':>18}")
for n in (100, 400, 500, 600, 1000):
    linear = linear_steps(n)
    quadratic = quadratic_steps(n)
    print(f"{n:>6} {linear:>10} {quadratic:>12} {str(linear < quadratic):>18}")
```

```output
     n       500n          n*n   линейный дешевле
   100      50000        10000              False
   400     200000       160000              False
   500     250000       250000              False
   600     300000       360000               True
  1000     500000      1000000               True
```

При `n = 500` функции равны, поэтому сравнение `linear < quadratic` даёт
`False`. Вывод для практики: если реальный размер входа меньше точки
пересечения, большая константа может быть выгоднее — но только до тех пор,
пока вход не вырос.

## 3. Порядок по замерам {#sol-ch52-03}

Отношения времени: `8 / 2 = 4` при удвоении `n` от 1000 до 2000, и
`32 / 8 = 4` при следующем удвоении. Удвоение входа увеличивает время
вчетверо — это `O(n ** 2)`. Линейный алгоритм дал бы отношение 2,
логарифмический — около 1, кубический — 8.

Чтобы отличить `O(n ** 2)` от `O(n ** 3)`, нужны как минимум ещё два-три
размера: при удвоении `n` квадратичный даст отношение около 4, кубический —
около 8. Полезно также проверить отношение на разных диапазонах: если оно
стабильно, порядок определён верно. Один замер не позволяет этого сделать —
он не содержит информации о росте.

## 4. Поиск в списке и множестве {#sol-ch52-04}

```python exec
comparisons = 0

class Key:
    def __init__(self, value):
        self.value = value
    def __hash__(self):
        return hash(self.value)
    def __eq__(self, other):
        global comparisons
        comparisons += 1
        return isinstance(other, Key) and self.value == other.value

target = Key(4999)
as_list = [Key(number) for number in range(5000)]
as_set = set(as_list)

comparisons = 0
print("в списке:", target in as_list, "сравнений:", comparisons)
comparisons = 0
print("в множестве:", target in as_set, "сравнений:", comparisons)
```

```output
в списке: True сравнений: 5000
в множестве: True сравнений: 1
```

Список сделал 5000 сравнений, множество — одно. Список уместен, когда важны
порядок и доступ по индексу, а проверок вхождения мало; если проверок много,
множество или словарь дешевле. Помните про память: множество хранит хеши и
занимает больше, чем список.

## 5. Амортизированная стоимость {#sol-ch52-05}

```python exec
def simulated_appends(count):
    size = 0
    capacity = 1
    copies = 0
    for _ in range(count):
        if size == capacity:
            copies += size
            capacity *= 2
        size += 1
    return copies

for n in (10, 100, 1000):
    copies = simulated_appends(n)
    print(f"n={n}: копирований {copies}, отношение {copies / n:.2f}")
```

```output
n=10: копирований 15, отношение 1.50
n=100: копирований 127, отношение 1.27
n=1000: копирований 1023, отношение 1.02
```

Докажем оценку. Копирования происходят, когда размер достигает ёмкости:
`1 + 2 + 4 + ... + n/2 < n`. Сумма геометрической прогрессии меньше `2n`,
значит на `n` добавлений приходится меньше `2n` копирований, то есть в
среднем меньше двух копирований на операцию — `O(1)` амортизированно.
Отношение в таблице всегда меньше двух, что и подтверждает оценку. Отдельный
`append` при этом может стоить `O(n)` — амортизация говорит о сумме, а не о
каждом вызове.

## 6. Дубликаты {#sol-ch52-06}

```python exec
def unique_naive(items):
    operations = 0
    seen = []
    for item in items:
        found = False
        for previous in seen:
            operations += 1
            if previous == item:
                found = True
                break
        if not found:
            seen.append(item)
    return len(seen), operations

def unique_set(items):
    operations = 0
    seen = set()
    for item in items:
        operations += 1
        seen.add(item)
    return len(seen), operations

data = [number % 1000 for number in range(2000)]
print("наивно:", unique_naive(data))
print("множество:", unique_set(data))
print("во сколько раз больше операций:", unique_naive(data)[1] // unique_set(data)[1])
```

```output
наивно: (1000, 1000000)
множество: (1000, 2000)
во сколько раз больше операций: 500
```

Наивная версия выполнила миллион сравнений, версия с множеством — 2000
добавлений. При удвоении `n` первая увеличит работу вчетверо, вторая — вдвое.
Именно поэтому проверку вхождения внутри цикла по списку считают классической
ошибкой: она превращает линейный алгоритм в квадратичный.

## 7. Выбор структуры {#sol-ch52-07}

1. **Словарь переводов.** `dict`: связь «ключ → значение», поиск `O(1)` в
   среднем. Список пар потребовал бы `O(n)` на поиск.
2. **Проверка «входил ли пользователь сегодня».** `set`: нужно только
   множество значений и быстрая проверка `O(1)`. Если дополнительно нужна
   дата последнего входа, это уже `dict`.
3. **Очередь задач: берут с начала, добавляют в конец.** `collections.deque`:
   `popleft` и `append` за `O(1)`. У списка `pop(0)` стоит `O(n)`, потому что
   сдвигает все элементы.
4. **Топ-10 результатов.** `heapq` (куча) или список с сортировкой при
   обновлении: нужен порядок, а не произвольный доступ. Для десяти элементов
   разница несущественна, но при тысячах обновлений куча даёт `O(log 10)` на
   вставку.

Общее правило: сначала выписать операции, которые будут частыми, затем
подобрать структуру, у которой эти операции дешёвые.

## 8. Двоичный поиск {#sol-ch52-08}

```python exec
import bisect

comparisons = 0

class Item:
    def __init__(self, value):
        self.value = value
    def __lt__(self, other):
        global comparisons
        comparisons += 1
        return self.value < other.value
    def __eq__(self, other):
        global comparisons
        comparisons += 1
        return isinstance(other, Item) and self.value == other.value

def manual_binary_search(items, target):
    global comparisons
    comparisons = 0
    low, high = 0, len(items) - 1
    while low <= high:
        middle = (low + high) // 2
        if items[middle] == target:
            return middle, comparisons
        if items[middle] < target:
            low = middle + 1
        else:
            high = middle - 1
    return -1, comparisons

data = [Item(number) for number in range(1024)]
print("вручную:", manual_binary_search(data, Item(777)))
comparisons = 0
print("bisect:", bisect.bisect_left(data, Item(777)), comparisons)
```

```output
вручную: (777, 17)
bisect: 777 10
```

Ручная версия сделала 17 сравнений, `bisect` — 10. Обе логарифмические: около
`log2(1024) = 10` шагов. Разница в константе: ручная версия на каждом шаге
сравнивает дважды (`==` и `<`), а `bisect` использует одно сравнение и
работает на C. Для 1024 элементов максимум около 10 шагов; для миллиона —
около 20. Именно поэтому удвоение данных добавляет один шаг.

## 9. Память или время {#sol-ch52-09}

```python exec
import sys

def squares_loop(limit):
    total = 0
    for number in range(limit):
        total += number * number
    return total

def squares_list(limit):
    return sum([number * number for number in range(limit)])

def squares_generator(limit):
    return sum(number * number for number in range(limit))

limit = 100_000
print("результат одинаковый:", squares_loop(limit) == squares_list(limit) == squares_generator(limit))
materialized = [number * number for number in range(limit)]
print("список квадратов:", sys.getsizeof(materialized), "байт")
print("пустой список:", sys.getsizeof([]), "байт")
```

```output
результат одинаковый: True
список квадратов: 800984 байт
пустой список: 56 байт
```

Версия со списком хранит все квадраты — `O(n)` памяти. Версия с генератором и
цикл с накоплением держат одно число — `O(1)`. Для `n = 10 ** 8` список из
`int` потребовал бы гигабайты только на ссылки, а вычисление в цикле — нет.
Вывод: если результат нужен целиком, материализация неизбежна; если нужна
только сумма, хранить список незачем.

## 10. Мини-задача: частотный анализ {#sol-ch52-10}

```python exec
words = "яблоко груша яблоко слива груша яблоко".split()
counts = {}
for word in words:
    counts[word] = counts.get(word, 0) + 1

repeated = [(word, count) for word, count in counts.items() if count > 1]
repeated.sort(key=lambda pair: pair[1], reverse=True)
print("повторяются:", repeated)
print("уникальных:", len(counts))
```

```output
повторяются: [('яблоко', 3), ('груша', 2)]
уникальных: 3
```

Подсчёт частот — один проход по словам и `O(1)` на обновление счётчика в
среднем, итого `O(n)`. Сортировка повторяющихся пар даёт `O(k log k)`, где `k`
— число различных слов; в худшем случае `k = n`, и тогда всё решение
`O(n log n)`. Избежать сортировки можно, если нужен только список повторных
слов без порядка: тогда достаточно фильтрации за `O(k)`. Сортировка нужна
именно для упорядочивания по частоте.

## Ответы на вопросы для самопроверки

1. `O(n log n)` — работа растёт примерно как `n`, умноженное на логарифм:
   так ведёт себя хорошая сортировка. Константы отброшены, потому что при
   больших `n` они не влияют на форму роста.
2. Лучший случай — минимальная работа (элемент найден первым), худший —
   максимальная (элемента нет), типичный — средний по реальным данным. Пример:
   поиск в списке.
3. Одна машина даёт абсолютное время, но не показывает, как поведение
   изменится при росте данных и на других условиях; инженерное решение
   опирается на рост.
4. Нужно измерить время на нескольких размерах (минимум трёх) и сравнить
   отношения: удвоение входа даёт ×2 для линейного, ×4 для квадратичного, ×1
   для константного.
5. Множество вычисляет хеш и обращается к корзине, поэтому число сравнений не
   зависит от размера; список просматривает элементы по одному.
6. Амортизированная сложность усредняет редкие дорогие перестройки по многим
   дешёвым операциям; отдельная операция всё равно может быть дорогой.
7. Материализация хуже, когда результат не нужен целиком или данных много:
   список занимает `O(n)` памяти, генератор — `O(1)`.
8. Выбор структуры — решение о сложности по требованиям задачи, принимаемое
   на этапе проектирования; преждевременная оптимизация — изменение кода без
   замера узкого места.
