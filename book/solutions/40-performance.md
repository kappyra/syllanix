# Решения к главе 40

Решения отделены от условий. В задачах о производительности главное — не
код, а порядок рассуждения: что измеряем, с чем сравниваем и почему верим
результату. Запускайте примеры и сверяйте счётчики: они детерминированы, в
отличие от времени работы.

## 1. Замер или догадка {#sol-ch40-01}

План бенчмарка состоит из пяти решений, и каждое нужно зафиксировать
письменно.

1. **Сценарий.** Что именно выполняется: одна функция, участок программы или
   весь запуск. Для функции указывают её аргументы и что считается
   результатом.
2. **Данные.** Размер и характер входа. Производительность на десяти
   элементах ничего не говорит о тысяче: алгоритм может иметь разную
   сложность в разных диапазонах.
3. **Повторы.** `timeit` по умолчанию делает пять раундов и берёт лучшее
   время. Для собственного замера делают не меньше пяти повторов и берут
   минимум: он меньше всего зашумлён фоновыми процессами.
4. **Базовая линия.** Число, с которым сравнивают: время до изменения кода
   на тех же данных. Без него «стало быстрее» — не утверждение, а ощущение.
5. **Условия.** Версия Python, машина, отсутствие отладчика и профилировщика.
   Профилировщик замедляет код, поэтому профиль и бенчмарк не смешивают.

Однократный замер в интерактивной сессии не годится по трём причинам: первый
запуск включает прогрев интерпретатора и импортов, один результат полностью
подвержен случайным задержкам системы, а без базовой линии и фиксированных
данных его нельзя воспроизвести. Бенчмарк — это эксперимент с контрольными
условиями, а не «посмотреть, сколько получилось».

## 2. Сложность на счётчиках {#sol-ch40-02}

Сравнения удобно считать через собственный класс: `sorted` вызывает `__lt__`,
а наш поиск максимума — `__gt__`.

```python exec
comparisons = 0

class Counted:
    def __init__(self, value):
        self.value = value
    def __lt__(self, other):
        global comparisons
        comparisons += 1
        return self.value < other.value
    def __gt__(self, other):
        global comparisons
        comparisons += 1
        return self.value > other.value

def max_sort(values):
    global comparisons
    comparisons = 0
    ordered = sorted(values)
    return ordered[-1].value, comparisons

def max_scan(values):
    global comparisons
    comparisons = 0
    best = values[0]
    for value in values[1:]:
        if value > best:
            best = value
    return best.value, comparisons

data = [Counted(((number * 7919) % 1000) - 500) for number in range(1000)]
print("сортировка:", max_sort(data))
print("один проход:", max_scan(data))
```

```output
сортировка: (499, 8532)
один проход: (499, 999)
```

Сортировка сделала 8532 сравнения, один проход — 999. Один проход — это
`O(n)`: число сравнений равно числу элементов минус один. Сортировка — это
`O(n log n)`: `1000 * log2(1000)` примерно равно десяти тысячам, и 8532
попадает в этот порядок. При удвоении списка число сравнений в первом случае
удвоится, во втором вырастет чуть больше чем вдвое. Функция `max` из
стандартной библиотеки решает ту же задачу за один проход.

## 3. Исправление бенчмарка {#sol-ch40-03}

Код измеряет не `process`, а подготовку данных вместе с обработкой. Строка
`data = build_data(100000)` стоит между запуском счётчика и вызовом
`process`, поэтому её время попадает в результат. Если `build_data` медленная,
вывод «функция стала быстрее» будет ошибочным: изменилась подготовка, а не
обработка.

Правильный замер: данные готовят до запуска счётчика, а измеряют только
интересующий вызов.

```python exec
from time import perf_counter

def build_data(limit):
    return list(range(limit))

def process(data):
    return sum(data)

data = build_data(100_000)
start = perf_counter()
result = process(data)
elapsed = perf_counter() - start
print("результат корректен:", result == sum(range(100_000)))
print("измерение неотрицательно:", elapsed >= 0)
```

```output
результат корректен: True
измерение неотрицательно: True
```

В учебном примере печатается только проверяемый инвариант: измеренное время
не может быть отрицательным, а результат совпадает с эталонным. Само значение
`elapsed` зависит от машины, поэтому его не выводят в проверяемый блок.

## 4. Чтение профиля {#sol-ch40-04}

Оптимизировать нужно `parse`. Она вызвана два раза, но это ничего не значит:
важно, что на неё приходится 0.4 с суммарного времени из 0.5 с. `validate`
вызывается 500 000 раз, но её суммарное время всего 0.1 с: каждая операция
дешёвая, и ускорение в два раза даст выигрыш около 0.05 с против 0.2 с у
`parse`.

Одного `tottime` недостаточно, потому что он не показывает, какие функции
вызваны изнутри. Если `parse` сама тратит мало, а большую часть времени
проводит в разборе регуляркой или в чтении, то `tottime` будет маленьким, а
`cumtime` — большим. Тогда оптимизировать надо не `parse`, а то, что она
вызывает. Поэтому профиль читают в двух проекциях: `cumtime` показывает
цепочку, `tottime` — точку.

## 5. Мемоизация своими руками {#sol-ch40-05}

```python exec
cache = {}
computations = 0

def memo_fib(n):
    global computations
    if n in cache:
        return cache[n]
    computations += 1
    value = n if n < 2 else memo_fib(n - 1) + memo_fib(n - 2)
    cache[n] = value
    return value

print("fib(15) =", memo_fib(15))
print("вычислений:", computations)
print("записей в кэше:", len(cache))
```

```output
fib(15) = 610
вычислений: 16
записей в кэше: 16
```

Для `n = 15` нужно всего 16 вычислений: значения от 0 до 15. Без кэша их было
бы 1973. Кэш устроен как словарь из главы 17: проверка `n in cache` идёт по
хешу. Поэтому мемоизация превращает экспоненциальное число вызовов `O(2 ** n)`
в линейное `O(n)`: каждое значение вычисляется ровно один раз, и повторный
обход уже посчитанных ветвей исчезает.

## 6. Хешируемость аргументов {#sol-ch40-06}

Кэш `lru_cache` хранит результаты в словаре, где ключ составлен из
аргументов. Ключ словаря должен быть хешируемым, а список — изменяемый тип без
`__hash__`, поэтому попытка кэшировать вызов со списком падает.

```python exec expect-error
from functools import lru_cache

@lru_cache(maxsize=None)
def total(items):
    return sum(items)

print(total([1, 2, 3]))
```

```output
TypeError: unhashable type: 'list'
```

Первое исправление — передавать неизменяемый эквивалент: кортеж. Второе —
не кэшировать функцию, которая принимает изменяемые данные, либо кэшировать
на уровне вызывающего кода по стабильному ключу.

```python exec
from functools import lru_cache

@lru_cache(maxsize=None)
def total(items):
    return sum(items)

print(total((1, 2, 3)))
print(total.cache_info())
```

```output
6
CacheInfo(hits=0, misses=1, maxsize=None, currsize=1)
```

## 7. Кэш с ограничением {#sol-ch40-07}

```python exec
from functools import lru_cache

@lru_cache(maxsize=3)
def compute(value):
    print("вычисляем", value)
    return value * 10

for value in (1, 2, 3, 4, 5):
    compute(value)
print("после первого прохода:", compute.cache_info())
for value in (1, 2):
    compute(value)
print("после повторов:", compute.cache_info())
```

```output
вычисляем 1
вычисляем 2
вычисляем 3
вычисляем 4
вычисляем 5
после первого прохода: CacheInfo(hits=0, misses=5, maxsize=3, currsize=3)
вычисляем 1
вычисляем 2
после повторов: CacheInfo(hits=0, misses=7, maxsize=3, currsize=3)
```

Попаданий нет вовсе. После пяти вызовов в кэше остались три последних
значения — `3`, `4`, `5`, — а `1` и `2` были вытеснены. Повторные вызовы снова
промахнулись и вытеснили `3` и `4`. Отсюда вывод: маленький `maxsize` при
разнообразных аргументах даёт нулевую пользу. Размер кэша подбирают по
рабочему распределению аргументов.

## 8. Узкое место {#sol-ch40-08}

Общее время: `0.6 + 0.3 + 0.1 = 1.0` с. Разбор ускорили вдвое: `0.3`
превратились в `0.15`. Новое время: `0.6 + 0.15 + 0.1 = 0.85` с. Ускорение
программы целиком: `1.0 / 0.85 ≈ 1.18`, то есть около 18 %.

Даже если бы разбор стал мгновенным, время упало бы до `0.7` с, а ускорение
составило бы `1.0 / 0.7 ≈ 1.43` — не более 43 %. Это закон Амдала: предел
ускорения задаёт доля, которую занимает оптимизируемая часть. Чтобы получить
большее, нужно браться за чтение файла, а не за разбор.

## 9. Сложность в среднем {#sol-ch40-09}

Множество ищет элемент по хешу: вычисляет хеш, определяет корзину и
сравнивает элементы внутри неё. Если хеши распределены равномерно, корзина
короткая, и поиск в среднем требует `O(1)`. Если все хеши совпадают, все
элементы попадают в одну корзину, и поиск превращается в линейный просмотр —
`O(n)`.

Пример класса с константным хешем:

```python exec
comparisons = 0

class CollidingKey:
    def __init__(self, value):
        self.value = value
    def __hash__(self):
        return 1
    def __eq__(self, other):
        global comparisons
        comparisons += 1
        return isinstance(other, CollidingKey) and self.value == other.value

keys = [CollidingKey(number) for number in range(50)]
unique = set(keys)
print("уникальных значений:", len(unique))
print("сравнений при вставке:", comparisons)
print("поиск последнего:", keys[-1] in unique)
```

```output
уникальных значений: 50
сравнений при вставке: 1656
поиск последнего: True
```

Пятьдесят элементов потребовали 1656 сравнений — почти квадратично. Множество
остаётся корректным, но перестаёт быть быстрым. Встроенные типы получают
хорошие хеши от своих значений, а свой класс наследует эту обязанность.
Правило: `__hash__` должен зависеть от всех полей, участвующих в `__eq__`, и
давать разные значения для разных объектов.

## 10. Мини-задача: ускорение отчёта {#sol-ch40-10}

```python exec
def report_naive(numbers):
    operations = 0
    total = 0
    for number in numbers:
        total += number
        operations += 1
    minimum = numbers[0]
    for number in numbers:
        operations += 1
        if number < minimum:
            minimum = number
    maximum = numbers[0]
    for number in numbers:
        operations += 1
        if number > maximum:
            maximum = number
    unique = []
    for number in numbers:
        operations += 1
        found = False
        for previous in unique:
            operations += 1
            if previous == number:
                found = True
                break
        if not found:
            unique.append(number)
    return total, minimum, maximum, len(unique), operations

def report_fast(numbers):
    operations = 0
    total = 0
    minimum = maximum = numbers[0]
    unique = set()
    for number in numbers:
        operations += 1
        total += number
        if number < minimum:
            minimum = number
        if number > maximum:
            maximum = number
        unique.add(number)
    return total, minimum, maximum, len(unique), operations

data = [number % 100 for number in range(2000)]
print("наивно:", report_naive(data))
print("оптимально:", report_fast(data))
```

```output
наивно: (99000, 0, 99, 100, 108900)
оптимально: (99000, 0, 99, 100, 2000)
```

Оба варианта дают одинаковый отчёт, но наивный выполнил 108 900 операций,
а оптимальный — 2000. Причина в проверке уникальности: наивная версия для
каждого элемента просматривает уже накопленный список, то есть работает за
`O(n ** 2)`. Оптимальная хранит множество и получает `O(1)` в среднем.
Сумма, минимум и максимум в обоих случаях считаются за `O(n)`, но в наивной
версии это три отдельных прохода вместо одного.

## Ответы на вопросы для самопроверки

1. Бенчмарк фиксирует условия, данные и число повторов, поэтому его можно
   воспроизвести и сравнить. Однократный замер зависит от прогрева и
   случайных задержек.
2. Один замер содержит шум; несколько повторов позволяют взять лучший
   результат, который меньше всего искажён помехами.
3. `O(n log n)` растёт почти линейно с небольшим множителем, `O(n ** 2)` —
   квадратично; на больших `n` разница становится решающей.
4. `tottime` — время в самой функции без вызванных; `cumtime` — включая
   вызванные функции.
5. По столбцу `ncalls`: большое число вызовов при малом времени на вызов
   означает, что дорога не операция, а их количество.
6. Узкое место ограничивает общую производительность; пока оно не устранено,
   оптимизация остального даёт малый эффект по закону Амдала.
7. Мемоизация вредит при нечистых функциях (устаревший результат), при
   нехешируемых аргументах (ошибка) и при большом разнообразии аргументов
   (память растёт без попаданий).
8. Кэш хранит результаты в словаре, а ключами словаря могут быть только
   хешируемые объекты.
