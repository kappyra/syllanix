# Решения к главе 32

Здесь показаны и сами проверки, и ход мысли: что именно фиксирует тест, какие
значения выбраны и почему. Запускайте код и меняйте данные — так видно, как
тест реагирует на ошибку.

## 1. Проверка без фреймворка {#sol-ch32-01}

```python exec
def is_even(number: int) -> bool:
    return number % 2 == 0


assert is_even(0) is True
assert is_even(7) is False
assert is_even(-4) is True
print("проверки прошли")
```

```output
проверки прошли
```

Сравнение через `is True` подчёркивает, что функция обязана вернуть именно
логическое значение, а не «истинное» число вроде `1`. Для учебного примера
это полезная строгость.

## 2. Прогнозирование падения {#sol-ch32-02}

Первый `assert` проходит: `5 / 2` равно `2.5`. Второй падает: `half(4)`
возвращает `2.0`, а сравнивается с `3`. Строка `"готово"` не выводится,
потому что выполнение прерывается на исключении.

```python exec expect-error
def half(value: int) -> float:
    return value / 2


assert half(5) == 2.5
assert half(4) == 3
print("готово")
```

```output
AssertionError
```

`AssertionError` без сообщения означает: условие ложно. Чтобы понять, какие
значения сравнивались, в реальном тесте добавляют пояснение:
`assert half(4) == 3, f"half(4)={half(4)}"`.

## 3. Тестовый случай по шагам {#sol-ch32-03}

```python exec
def clamp(value: int, low: int, high: int) -> int:
    if value < low:
        return low
    if value > high:
        return high
    return value


# подготовка
inside, below, above = 5, -1, 42

# действие и проверка
assert clamp(inside, 0, 10) == 5
assert clamp(below, 0, 10) == 0
assert clamp(above, 0, 10) == 10
print("три случая проверены")
```

```output
три случая проверены
```

Внутри диапазона функция возвращает исходное значение, ниже — нижнюю границу,
выше — верхнюю. Именно эти три поведения и нужно закрепить: одного «среднего»
случая недостаточно, потому что обе границы — отдельные ветки.

## 4. Параметризация без pytest {#sol-ch32-04}

```python exec
def normalize_space(text: str) -> str:
    return " ".join(text.split())


cases = [(" a  b ", "a b"), ("a\tb", "a b"), ("   ", "")]
for index, (raw, expected) in enumerate(cases, start=1):
    actual = normalize_space(raw)
    assert actual == expected, f"случай {index}: ожидалось {expected!r}, получено {actual!r}"
print("случаев проверено:", len(cases))
```

```output
случаев проверено: 3
```

`str.split()` без аргументов разбивает по любым пробельным символам и
отбрасывает пустые фрагменты, поэтому `" ".join(...)` нормализует строку.
Цикл по таблице — ручная параметризация: pytest делает то же самое, но
показывает в отчёте, какой именно набор упал.

## 5. Красный — зелёный {#sol-ch32-05}

Сначала падающий тест на наивной реализации: она заменяет пробелы дефисами,
но не убирает пунктуацию и дефисы по краям.

```python exec expect-error
def slugify(title: str) -> str:
    return title.lower().replace(" ", "-")


assert slugify("  Привет, Мир  ") == "привет-мир"
```

```output
AssertionError
```

Теперь минимальная реализация, проходящая тест: всё, что не буква и не
цифра, заменяется на дефис, а края очищаются.

```python exec
import re


def slugify(title: str) -> str:
    text = title.lower()
    text = re.sub(r"[^a-zа-яё0-9]+", "-", text)
    return text.strip("-")


print(slugify("  Привет, Мир  "))
print(slugify("Python 3.14 — это здорово"))
```

```output
привет-мир
python-3-14-это-здорово
```

Порядок шагов TDD важен: тест был написан до реализации и сначала падал.
Иначе легко подогнать проверку под то, что получилось, и не заметить
проблему с краями.

## 6. Ожидаемое исключение {#sol-ch32-06}

В тестах pytest исключение проверяют через `pytest.raises`. Тест ниже проходит,
только если `ValueError` действительно поднят, а сообщение содержит слово
«диапазон»:

```python
import pytest

from percents import parse_percent


def test_parse_percent_ok():
    assert parse_percent("42") == 42


def test_parse_percent_out_of_range():
    with pytest.raises(ValueError, match="диапазон"):
        parse_percent("140")
```

`match` — регулярное выражение, которое ищется в тексте сообщения, поэтому не
приходится сравнивать всю строку целиком: её можно уточнять, не ломая тест.
Если исключения не будет, `pytest.raises` сам провалит проверку, так что
отдельная ветка `else` не нужна.

Без pytest ту же проверку собирают вручную — и здесь ветка `else` обязательна:

```python exec
def parse_percent(text: str) -> int:
    value = int(text)
    if not 0 <= value <= 100:
        raise ValueError(f"процент вне диапазона: {value}")
    return value


assert parse_percent("42") == 42
try:
    parse_percent("140")
except ValueError:
    pass
else:
    raise AssertionError("ожидалось ValueError")
print("проверки прошли")
```

```output
проверки прошли
```

Ветка `else` выполняется, только если исключения не было, — поэтому именно
там ставится проваливающая проверка. Без неё тест «прошёл бы» и в случае,
когда `ValueError` не поднялся вовсе.

## 7. Регрессия {#sol-ch32-07}

Воспроизведём дефект: пользователь прав, скидка считается неверно.

```python exec expect-error
def discount(total: int, percent: int) -> int:
    return total - total * percent // 100


# пользователь ожидает 899, а получает 900
assert discount(999, 10) == 899
```

```output
AssertionError
```

Причина в порядке округления. Старая формула сначала округляет вниз величину
скидки: `999 * 10 // 100 = 99`, и вычитает её из полной суммы. Новая формула
сначала вычисляет итоговую долю и только потом округляет её:
`999 * 90 // 100 = 899`. Пользователь видит цену, а не скидку, поэтому
округлять нужно итог.

```python exec
def discount(total: int, percent: int) -> int:
    if not 0 <= percent <= 100:
        raise ValueError("процент вне диапазона")
    return total * (100 - percent) // 100


assert discount(1000, 10) == 900
assert discount(999, 10) == 899
assert discount(999, 33) == 669
print("регрессия закрыта")
```

```output
регрессия закрыта
```

Тест `discount(999, 10) == 899` остаётся в наборе навсегда: он фиксирует
исправленное поведение и не даёт вернуть старую формулу.

## 8. Мок зависимости {#sol-ch32-08}

```python exec
from unittest.mock import patch


def current_hour() -> int:
    return 12


def greeting() -> str:
    hour = current_hour()
    if hour < 12:
        return "Доброе утро"
    if hour < 18:
        return "Добрый день"
    return "Добрый вечер"


with patch("__main__.current_hour", return_value=9):
    print(greeting())
with patch("__main__.current_hour", return_value=21):
    print(greeting())
```

```output
Доброе утро
Добрый вечер
```

Заглушка делает тест детерминированным: настоящая функция вернула бы текущий
час, и результат зависел бы от времени запуска. Мок заменяет только источник
времени; логика выбора приветствия проверяется по-настоящему.

## 9. Анализ покрытия {#sol-ch32-09}

Единственный тест исполняет первую ветку `value > 0` и возвращает `"плюс"`.
Строки `return "минус"` и `return "ноль"` не исполняются, поэтому покрытие
ветвей неполное: из трёх возможных возвратов проверен один. Одним тестом
покрыть все ветки нельзя, потому что функция возвращает ровно одно значение,
а ветвей три — нужны три вызова с разными знаками.

```python exec
def sign(value: int) -> str:
    if value > 0:
        return "плюс"
    if value < 0:
        return "минус"
    return "ноль"


assert sign(5) == "плюс"
assert sign(-5) == "минус"
assert sign(0) == "ноль"
print("все ветки проверены")
```

```output
все ветки проверены
```

Покрытие показывало бы исполненные строки, но не качество проверок. Даже
стопроцентное покрытие строк не гарантирует, что результаты сравнивались:
можно вызвать каждую ветку и не проверить ни одного возврата.

## 10. Мини-проект: набор тестов {#sol-ch32-10}

```python exec
def to_fahrenheit(celsius: float) -> float:
    return celsius * 9 / 5 + 32


def test_freezing() -> None:
    assert to_fahrenheit(0) == 32.0


def test_boiling() -> None:
    assert to_fahrenheit(100) == 212.0


def test_negative() -> None:
    assert to_fahrenheit(-40) == -40.0


def test_fractional() -> None:
    assert round(to_fahrenheit(36.6), 2) == 97.88


tests = [test_freezing, test_boiling, test_negative, test_fractional]
for test in tests:
    test()
print("пройдено тестов:", len(tests))
```

```output
пройдено тестов: 4
```

Проверка `-40` ценна тем, что это единственная точка, где шкалы совпадают:
ошибку в коэффициенте она ловит иначе, чем точки замерзания и кипения.
Дробное значение проверяет вычисление с плавающей точкой. Сравнивать
вещественные числа «в лоб» рискованно: `36.6 * 9 / 5 + 32` даёт
`97.88000000000001`, поэтому результат округляют до нужного числа знаков.

Требование про `TypeError` при нечисловом аргументе:

```python exec expect-error
def to_fahrenheit(celsius: float) -> float:
    return celsius * 9 / 5 + 32


to_fahrenheit("0")
```

```output
TypeError: unsupported operand type(s) for /: 'str' and 'int'
```

```python exec
def to_fahrenheit(celsius: float) -> float:
    return celsius * 9 / 5 + 32


try:
    to_fahrenheit("0")
except TypeError:
    print("нечисловой аргумент отклонён")
```

```output
нечисловой аргумент отклонён
```

## Ответы на вопросы для самопроверки

1. Модульный тест автоматизирован и повторяем: он сам сравнивает результат и
   падает при расхождении. Ручная проверка в терминале не сохраняется и не
   защищает от повторного появления дефекта.
2. Тестовый случай включает подготовку, действие и проверку. Смешивать
   несколько случаев в одном тесте плохо: при падении непонятно, какой именно
   сценарий сломался.
3. Фикстура убирает дублирование подготовки и гарантирует очистку. Без неё
   состояние течёт между тестами, и набор становится зависимым от порядка.
4. Параметризация создаёт отдельный тест на каждый набор данных, поэтому в
   отчёте видно, какая именно комбинация входных значений упала.
5. Тест до кода фиксирует требование. Тест после кода легко подогнать под
   текущее поведение, включая ошибочное.
6. Покрытие показывает, какая доля кода исполнялась тестами. Оно не
   показывает, проверяются ли результаты и покрыты ли все ветви.
7. Мок полезен для внешних и нестабильных зависимостей: сети, времени, базы.
   Если замокано всё, тест перестаёт проверять программу и проверяет только
   заготовленные ответы.
