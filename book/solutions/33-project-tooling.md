# Решения к главе 33

Решения показывают, как проверять настройки проекта кодом и как рассуждать о
воспроизводимости. Команды установки приведены в блоках `console`: они не
исполняются автоматически, потому что меняют окружение машины.

## 1. Разбор структуры {#sol-ch33-01}

В исходной раскладке три проблемы.

1. Пакет `shop/` лежит в корне, поэтому при запуске из корня импортируется
   локальная копия, а не установленная. Тесты проверяют не то, что получит
   пользователь.
2. `test_shop.py` лежит в корне рядом с пакетом: тест не отделён от кода и
   попадёт в сборку, если её настроить небрежно.
3. Зависимости описаны в `requirements.txt` без версий и без разделения на
   основные и разработческие; версия Python не зафиксирована.

Исправленная структура:

```text
shop/
├── pyproject.toml
├── uv.lock
├── README.md
├── src/
│   └── shop/
│       └── __init__.py
└── tests/
    └── test_shop.py
```

Зависимости переезжают в `pyproject.toml`, а `.venv` добавляется в
`.gitignore`: окружение восстанавливается, а не хранится в репозитории.

## 2. Чтение манифеста {#sol-ch33-02}

```python exec
import tomllib


def read_project(text: str) -> dict[str, object]:
    data = tomllib.loads(text)
    project = data["project"]
    return {
        "name": project["name"],
        "version": project["version"],
        "requires_python": project["requires-python"],
        "dependencies": project["dependencies"],
    }


manifest = """
[project]
name = "notes"
version = "0.3.1"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27", "rich>=13.7"]
"""

print(read_project(manifest))
```

```output
{'name': 'notes', 'version': '0.3.1', 'requires_python': '>=3.11', 'dependencies': ['httpx>=0.27', 'rich>=13.7']}
```

`tomllib.loads` принимает строку и возвращает словарь. Обратите внимание на
ключ `requires-python`: в TOML дефис допустим в имени, а обращаться к нему
нужно через индексацию, а не через точку.

## 3. Сравнение версий {#sol-ch33-03}

```python exec
def parse(text: str) -> tuple[int, int, int]:
    major, minor, patch = text.split(".")
    return int(major), int(minor), int(patch)


def is_newer(candidate: str, current: str) -> bool:
    return parse(candidate) > parse(current)


print(is_newer("1.10.0", "1.9.2"))
print(is_newer("2.0.0", "1.99.99"))
print(is_newer("1.4.2", "1.4.2"))
```

```output
True
True
False
```

Сравнение кортежей целых чисел работает покомпонентно: сначала `major`, затем
`minor`, затем `patch`. Поэтому `1.10.0` больше `1.9.2`, хотя как строка
`"1.10.0"` меньше. Разбор на числа обязателен — иначе лексикографическое
сравнение даст неверный порядок.

## 4. Прогнозирование версии {#sol-ch33-04}

Добавление возможности без поломки API увеличивает `MINOR`: `1.4.2` →
`1.5.0`. Исправления ошибок увеличивают `PATCH`, но если в том же выпуске есть
новая возможность, достаточно `MINOR`. Если пришлось бы изменить сигнатуру
публичной функции несовместимым образом, нужен `MAJOR`: `1.4.2` → `2.0.0`.
Причина в обещании: пользователь, увидев `MINOR`, вправе обновиться без
правок кода, а `MAJOR` предупреждает, что правки понадобятся. Предварительные
выпуски помечают суффиксом вроде `rc1`, чтобы такие обновления не попадали в
production случайно.

## 5. Манифест с нуля {#sol-ch33-05}

```toml
[project]
name = "weather"
version = "0.1.0"
description = "Погода из командной строки"
requires-python = ">=3.12"
dependencies = ["httpx>=0.27"]

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff>=0.6"]

[project.scripts]
weather = "weather.cli:main"
```

Проверим, что файл разбирается и содержит нужные поля:

```python exec
import tomllib

raw = b"""
[project]
name = "weather"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["httpx>=0.27"]
"""

data = tomllib.loads(raw.decode())["project"]
print(data["requires-python"])
print(len(data["dependencies"]))
```

```output
>=3.12
1
```

В настоящем файле `[project.optional-dependencies]` и `[project.scripts]`
заполняются так же, как в примере. Проверка через `tomllib` ловит опечатки в
структуре раньше, чем менеджер пакетов.

## 6. Изоляция окружения {#sol-ch33-06}

Если две версии одной библиотеки поставить в системный Python, они начнут
перезаписывать друг друга: при установке второй пакет заменит файлы первой.
Проект, рассчитанный на старую версию, сломается без изменений в его коде.
Виртуальное окружение решает конфликт, потому что у каждого проекта свой
каталог пакетов и свой `sys.path`: интерпретатор видит только пакеты,
установленные в активированное окружение.

Чистое окружение создаётся так:

```console
$ python -m venv .venv
$ source .venv/bin/activate
(.venv) $ python -m pip install -e ".[dev]"
(.venv) $ pytest -q
```

После `deactivate` система возвращается в исходное состояние. Каталог `.venv`
можно удалить и собрать заново — это безопасно, потому что требования
зафиксированы в манифесте.

## 7. Манифест и блокировка {#sol-ch33-07}

`pyproject.toml` выражает намерение: «нужен `httpx` не ниже 0.27». Диапазон
позволяет получать исправления безопасности и совместимые улучшения, не меняя
манифест. Файл блокировки выражает факт: «при последнем разрешении выбрана
версия 0.27.2 с такими хешами, и все транзитивные зависимости тоже
зафиксированы». Блокировка обеспечивает воспроизводимость: установка на другой
машине даёт тот же набор пакетов, а не «что-нибудь совместимое».

Если удалить файл блокировки, менеджер пакетов разрешит зависимости заново по
диапазонам. Сегодня это может дать одну версию, завтра другую; ошибка,
воспроизводимая у одного разработчика, исчезнет у другого. Поэтому блокировку
коммитят, а обновляют осознанно — отдельным изменением с прогоном тестов.

## 8. Линтер и форматтер {#sol-ch33-08}

Форматтер исправит кавычки и переносы, но не станет менять смысл кода.
Неиспользуемый импорт он, как правило, не удаляет: это не форматирование, а
изменение программы. Линтер найдёт неиспользуемый импорт и, в зависимости от
правил, длинную строку; длину строки форматтер тоже может обработать, если она
превышает настроенный `line-length`.

Порядок запуска: сначала форматтер, затем линтер. Если сделать наоборот,
линтер сообщит о стилевых нарушениях, которые форматтер всё равно исправит, и
отчёт станет шумным. Проверка длины строки без внешних инструментов:

```python exec
lines = [
    "import os",
    "result = compute_total_price(items, discount, tax, shipping, currency, region)",
]
limit = 60
for number, line in enumerate(lines, start=1):
    if len(line) > limit:
        print(f"строка {number}: {len(line)} символов, лимит {limit}")
```

```output
строка 2: 78 символов, лимит 60
```

## 9. Версии зависимостей {#sol-ch33-09}

```python exec
def parse(text: str) -> tuple[int, int, int]:
    parts = [int(part) for part in text.split(".")]
    while len(parts) < 3:
        parts.append(0)
    return parts[0], parts[1], parts[2]


def check_requirement(requirement: str, installed: str) -> bool:
    for operator in (">=", "==", ">"):
        if operator in requirement:
            required = requirement.split(operator, 1)[1].strip()
            current = parse(installed)
            target = parse(required)
            if operator == ">=":
                return current >= target
            if operator == "==":
                return current == target
            return current > target
    raise ValueError(f"неизвестная спецификация: {requirement}")


print(check_requirement("httpx>=0.27", "0.27.2"))
print(check_requirement("httpx==0.27.0", "0.27.2"))
print(check_requirement("httpx>0.28", "0.27.2"))
```

```output
True
False
False
```

Первое требование выполнено: установленная версия новее минимальной. Второе и
третье — нет. Проверка операторов идёт от длинных к коротким, иначе `>`
перехватил бы `>=` и разбор сломался бы.

## 10. Мини-проект: каркас проекта {#sol-ch33-10}

Структура проекта `budget`:

```text
budget/
├── pyproject.toml
├── uv.lock
├── README.md
├── src/
│   └── budget/
│       ├── __init__.py
│       ├── cli.py
│       └── reports.py
└── tests/
    ├── test_cli.py
    └── test_reports.py
```

Манифест:

```toml
[project]
name = "budget"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = []

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff>=0.6"]

[project.scripts]
budget = "budget.cli:main"
```

Порядок действий нового участника:

```console
$ git clone <адрес-репозитория> budget
$ cd budget
$ uv sync
$ uv run pytest -q
$ uv run budget --help
```

Тесты лежат в `tests/` и повторяют имена модулей: `test_cli.py` проверяет
`cli.py`. Точка входа объявлена в `[project.scripts]`, поэтому команда `budget`
доступна после установки. README содержит эти же команды: одна установка,
один запуск тестов, один запуск программы. Воспроизводимость обеспечивают
`pyproject.toml` и `uv.lock`, а `.venv` каждый создаёт локально.

## Ответы на вопросы для самопроверки

1. Окружение изолирует пакеты проекта от системных и от других проектов:
   версии не конфликтуют, а установка воспроизводима.
2. Манифест описывает требования и настройки, блокировка фиксирует точные
   версии и хеши, выбранные при разрешении.
3. Транзитивная зависимость нужна другой зависимости; без её фиксации
   итоговый набор версий перестаёт быть воспроизводимым.
4. Форматтер приводит код к единому виду автоматически; линтер ищет ошибки и
   нарушения правил, которые нельзя исправить форматированием.
5. Версии сравниваются как наборы чисел, а не как строки: `10` больше `9`.
6. Увеличение `MAJOR` предупреждает о несовместимом изменении API.
7. `.venv` содержит бинарники и абсолютные пути, зависит от машины и
   восстанавливается из манифеста; хранить его в git бессмысленно.
